# Подготовка production-развёртывания

Этот документ фиксирует текущую схему production-запуска Leave Desk на одном
VPS. GitHub Actions собирает Docker-образ прошедшего CI коммита, публикует его
в приватном GHCR и разворачивает через Docker Compose; исходный код и
сборочные зависимости на сервер не копируются.

## Что есть в проекте сейчас

- Rails-приложение запускается через Puma; CI проверяет тесты, стиль,
  зависимости и безопасность командой `bin/ci`.
- Для production в `config/database.yml` описаны PostgreSQL-базы для основного
  приложения, Solid Cache, Solid Queue и Solid Cable. Отдельный сервис `migrate`
  подготавливает их с административными правами; `web` использует роль
  `leave_desk_app` только с правами чтения и записи данных.
- Health check доступен по пути `/up`.
- Production-логи направляются в stdout. Rails фильтрует чувствительные
  параметры; отдельный журнал запросов Thruster отключается через
  `LOG_REQUESTS=false`, потому что он записывал исходную строку URL. Не
  добавлять в логи комментарии заявок, пароли и другие персональные данные.
  Docker-логи `web` ограничены тремя файлами по 10 МиБ; старые логи требуют
  ограниченного доступа до штатного удаления.
  На production 14 октября 2026 года после выпуска `7a62189` проверены обе
  настройки. Запрос с синтетическими значениями вернул HTTP 200: в журнале
  есть фильтрованная строка Rails, а исходных значений и строки Thruster
  `Request` нет. На корневом разделе оставалось около 7,1 ГиБ свободно.
- В production-конфигурации включён локальный Active Storage. При появлении
  пользовательских файлов или запуске нескольких экземпляров приложения нужно
  обеспечить надёжное общее хранилище и резервирование либо заменить этот
  backend.
- Caddy завершает TLS и перенаправляет HTTP на HTTPS. Публичной точкой входа
  служит IP-адрес из серверной переменной `LEAVE_DESK_PUBLIC_HOST`; сертификат
  Let’s Encrypt с IP SAN имеет
  короткий срок действия и автоматически продлевается Caddy.
- Приложение привязано к `127.0.0.1:3000` и недоступно напрямую извне; Caddy
  обращается к нему по внутренней Docker-сети.
- Фоновые задания пока не используются. Solid Queue нельзя включать до
  добавления его конфигурации и схемы базы данных.
- Демонстрационные учётные записи создаются только в development. Production
  нельзя инициализировать seed-данными.

## Решения до настройки инфраструктуры

Перед первым production-развёртыванием зафиксировать:

| Решение | Статус |
| --- | --- |
| Платформа приложения и способ сборки/запуска | Один Ubuntu VPS, Docker Compose, образ из приватного GHCR |
| Публичный домен, TLS и схема reverse proxy | HTTPS по IP через Caddy и Let’s Encrypt |
| PostgreSQL: размещение, версии, подключения и управление ролями | PostgreSQL 16 в закрытом Docker-сервисе на том же VPS |
| Размещение Solid Cache, Solid Queue и Solid Cable | Отдельные базы созданы; Solid Queue отключён до появления фоновых задач |
| Хранилище файлов и требуемая политика доступа | Docker volume на VPS; пересмотреть до использования загрузок |
| Частота резервного копирования, срок хранения, RPO и RTO | [Состояние C13](database-backup-and-restore.md): ежедневная локальная копия в 02:00 UTC, хранение 7 суток, ожидаемый RPO около 24 часов. GitHub Actions ежедневно проверяет копию и место. Время восстановления одной БД измерено; RTO всего приложения не подтверждён. Внешнее хранилище и доставка оповещений человеку остаются открытыми. |
| Доступы к журналам и мониторингу | Docker logs через root SSH; внешний мониторинг не выбран |
| Процедура выпуска и отката приложения | GitHub Actions разворачивает SHA-тег; откат — возврат тега предыдущего образа |

Значения секретов должны задаваться средствами выбранной платформы и не
попадать в Git, логи, CI-вывод или документацию. В production не использовать
демонстрационный пароль из seeds.

Перед первым запуском задайте в серверном `.env` уникальный `SECRET_KEY_BASE`,
созданный командой `bin/rails secret` в локальной копии проекта. Пустое значение
и прежняя заглушка из
шаблона отклоняются при запуске. Если заглушка уже использовалась в production,
замените ключ и завершите действующие серверные сессии: прежние подписанные
cookie больше не должны давать доступ.

14 октября 2026 года серверная настройка проверена без вывода значения:
`SECRET_KEY_BASE` задан один раз, не пуст, не равен прежней заглушке и имеет
длину не меньше 64 символов. Случайность значения этой проверкой не доказана.

Задайте отдельный случайный `LEAVE_DESK_RUNTIME_DATABASE_PASSWORD` в серверном
`.env`; он должен отличаться от `LEAVE_DESK_BOOTSTRAP_DATABASE_PASSWORD`. Первый
запуск с новой схемой доступа выполняйте так:

```sh
docker compose pull web migrate
docker compose run --rm migrate
docker compose up -d --no-deps web
```

`migrate` выполняет `db:prepare`, создаёт ограниченную роль и выдаёт ей права
на четыре базы. Команда повторяемая; запускайте её до каждого обновления `web`.
На существующем томе PostgreSQL bootstrap-роль `leave_desk` остаётся владельцем
баз и таблиц. Пароль bootstrap-роли доступен только сервису `migrate` и БД;
сервис `web` его не получает. После первого выпуска проверьте на сервере, что
роль приложения не имеет `SUPERUSER`, `CREATEDB` и `CREATEROLE`, может читать и
изменять данные, но не может создавать таблицы. Это подтверждено 14 октября
2026 года для всех четырёх баз; `web` подключился как `leave_desk_app`.

## Автоматический выпуск

В GitHub необходимо создать environment `production` со следующими secrets:

| Secret | Назначение |
| --- | --- |
| `DEPLOY_HOST` | Публичный адрес VPS |
| `DEPLOY_PORT` | SSH-порт VPS |
| `DEPLOY_USER` | Пользователь SSH, сейчас `root` |
| `DEPLOY_SSH_PRIVATE_KEY` | Закрытый ключ отдельной учётной записи CI |
| `DEPLOY_SSH_KNOWN_HOSTS` | Проверенная строка host key для адреса и порта VPS |

Workflow `.github/workflows/deploy.yml` запускается после успешного `CI` на
`main`. Он публикует два тега: SHA коммита для выпуска и `latest` для удобства.
Compose всегда получает SHA-тег, поэтому работающий релиз не зависит от
дальнейшего перемещения `latest`.

Во время выпуска workflow копирует только `deploy/compose.yml` и
`deploy/Caddyfile`, временно авторизует Docker на VPS токеном текущего запуска,
обновляет `LEAVE_DESK_IMAGE` в серверном `.env`, запускает сервис `migrate`,
затем перезапускает `web` и
проверяет `/up`. Production-секреты приложения остаются только в серверном
`.env`; workflow их не читает.

Для отката нужно указать в серверном `.env` ранее выпущенный SHA-тег и выполнить:

```sh
docker compose pull web
docker compose up -d --no-deps web
set -a; . ./.env; set +a
curl --fail --header "Host: $LEAVE_DESK_PUBLIC_HOST" http://127.0.0.1:3000/up
```

## Чек-лист первого выпуска

### До выпуска

- [ ] Все решения из таблицы выше приняты и записаны.
- [x] Для production заданы секреты Rails и параметры подключения к базам через
  защищённое хранилище платформы.
- [x] Настроены HTTPS, доверие только к ожидаемым host/proxy и проверка
  редиректа HTTP → HTTPS.
- [ ] Схема запуска Solid Queue определена: отдельный worker или поддерживаемый
  проектом режим в Puma; подтверждена обработка очереди после перезапуска.
- [x] Выполнен `bin/ci` на том же коммите, который планируется выпустить.
- [x] Создана резервная копия и успешно проверено восстановление в изолированную
  базу по инструкции [резервного копирования](database-backup-and-restore.md).
- [ ] Определены ответственные за выпуск, откат и доступ к резервным копиям.

### Выпуск

- [x] Развернуть приложение выбранным способом и выполнить штатную подготовку
  всех настроенных баз и миграций.
- [x] Убедиться, что `/up` возвращает успешный ответ, а приложение подключается
  ко всем необходимым базам.
- [ ] Выполнить smoke-проверку входа, создания заявки, согласования и встроенного
  уведомления на тестовых учётных записях без демонстрационных персональных
  данных.
- [ ] Проверить, что фоновые задания обрабатываются, ошибки доступны в
  ограниченных по доступу логах, а секреты и данные сотрудников не выводятся.
- [ ] Зафиксировать коммит, время выпуска, результат проверок и ответственного.

### Откат

- [ ] Откат приложения выполнять на предыдущий проверенный release.
- [ ] Не откатывать схему БД автоматически: миграции должны быть обратно
  совместимы с предыдущим release либо иметь отдельную утверждённую процедуру.
- [ ] При повреждении данных следовать процедуре восстановления; не выполнять
  очистку production-базы как шаг обычного отката.

## Критерий готовности

Развёртывание можно планировать, когда решения до настройки инфраструктуры
приняты, все пункты первого выпуска проверены, восстановление из резервной
копии отрепетировано, а выпуск и откат назначены ответственным людям.
