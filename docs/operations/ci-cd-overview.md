# Сборка и сетевой доступ к деплою

## Откуда выполняется деплой

Деплой запускается с GitHub-hosted runner и подключается к публичному адресу
VPS по SSH-порту, заданному в GitHub Environment `production`. IP-адреса таких
runner динамические, поэтому SSH-порт VPS должен принимать соединения не с
одного фиксированного адреса, а из интернета.

Подключение защищают:

- отдельный SSH-ключ GitHub Actions;
- проверка host key VPS через `known_hosts`;
- secrets GitHub Environment;
- авторизация по ключу вместо передачи SSH-пароля в workflow.

Для дополнительной защиты следует запретить вход `root` по паролю, оставить
только авторизацию ключами, настроить firewall и fail2ban. Следующий шаг
усиления изоляции — отдельный пользователь `deploy` с минимально необходимыми
правами вместо `root`.

Само приложение доступно пользователям из интернета через порты 80 и 443.

## Как устроены сборка и выпуск

### 1. CI

При каждом pull request и push в `main` запускается
`.github/workflows/ci.yml`. Параллельно выполняются:

- `scan_ruby` — Brakeman и аудит зависимостей;
- `lint` — RuboCop;
- `test` — тесты Rails с PostgreSQL 16.

Если хотя бы одна проверка завершается ошибкой, автоматический выпуск не
запускается. Отдельного job `system-test` пока нет, поскольку проект не содержит
каталог `test/system`.

### 2. Docker-образ

После успешного CI для push в `main` запускается
`.github/workflows/deploy.yml`. Workflow проверяет, что прошедший CI коммит
по-прежнему находится на вершине `main`, и собирает его образ по корневому
`Dockerfile`. Workflow также можно запустить вручную через `workflow_dispatch`.

Dockerfile использует многоступенчатую сборку:

1. Базовый слой основан на `ruby:4.0.2-slim`.
2. Во временном build-слое устанавливаются компиляторы и build-зависимости.
3. Выполняются `bundle install`, компиляция Bootsnap и Rails assets.
4. Готовое приложение и gems переносятся в облегчённый runtime-слой.
5. Приложение запускается от непривилегированного пользователя `rails`.

Build-инструменты временного слоя в итоговый образ не попадают. BuildKit
сохраняет слои в кэше GitHub Actions для ускорения следующих сборок.

### 3. GHCR

Образ публикуется в GitHub Container Registry с двумя тегами:

```text
ghcr.io/sas2job/leave-desk:<полный SHA коммита>
ghcr.io/sas2job/leave-desk:latest
```

Production использует неизменяемый SHA-тег. Тег `latest` предназначен только
для удобства и не определяет работающий релиз.

### 4. VPS

GitHub Actions выполняет следующие действия:

1. Настраивает временный SSH-ключ и проверяет host key сервера.
2. Загружает `deploy/compose.yml`, `deploy/Caddyfile`, служебные скрипты и
   service/timer-файлы в отдельный `.incoming`-каталог, проверяет SHA-256
   manifest и атомарно переключает ссылку `current` на полный релиз.
3. Временно авторизует Docker на VPS в GHCR токеном текущего workflow.
4. Читает SHA-тег из `current/release.env`; секреты остаются в серверном `.env`.
5. Выполняет:

   ```sh
   ./current/compose.sh pull web migrate
   ./current/compose.sh run --rm migrate
   ./current/compose.sh up -d --no-deps web
   ```

PostgreSQL при этом не перезапускается. Проверенный `Caddyfile` публикуется
атомарно внутри каталога bind mount; Caddy согласуется через Compose и получает
явный reload. После скачивания образа авторизация GHCR удаляется с VPS.

Откат через `current/rollback.sh` использует локальный SHA-образ без входа в
GHCR. Если образ уже удалён из cache, оператор передаёт read-only токен через
stdin; скрипт использует и удаляет отдельный временный Docker config.

### 5. Проверка выпуска

Workflow ждёт запуска Rails и проверяет `/up` через локальный порт приложения.
В запрос передаётся разрешённый host из серверного `.env`. Каждая попытка
ограничена двумя секундами на соединение и пятью секундами на весь HTTP-запрос,
а вся серия — жёстким сроком 90 секунд. Если endpoint не отвечает успешно за
30 попыток или общий срок истекает, deploy сообщает причину, завершается
ошибкой и выводит последние 100 строк логов контейнера `web`.

## Где находятся секреты

В GitHub Environment `production` хранятся:

- `DEPLOY_HOST`;
- `DEPLOY_PORT`;
- `DEPLOY_USER`;
- `DEPLOY_SSH_PRIVATE_KEY`;
- `DEPLOY_SSH_KNOWN_HOSTS`.

Пароль PostgreSQL, `SECRET_KEY_BASE` и публичный адрес приложения остаются в
серверном `.env`. Они не передаются в репозиторий и не читаются workflow.

Итоговый процесс: успешный push в `main` → CI → сборка образа → публикация в
GHCR → миграции → обновление контейнера `web` → health check.
