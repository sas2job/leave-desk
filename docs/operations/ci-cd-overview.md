# Сборка и сетевой доступ к деплою

## Откуда выполняется деплой

Деплой запускается с GitHub-hosted runner и подключается к публичному адресу
VPS по SSH-порту, заданному в GitHub Environment `production`. IP-адреса таких
runner динамические, поэтому SSH-порт VPS должен принимать соединения не с
одного фиксированного адреса, а из интернета.

Подключение защищают:

- отдельный SSH-ключ GitHub Actions;
- проверка host key VPS через `known_hosts`;
- secrets GitHub Environment;
- авторизация по ключу вместо передачи SSH-пароля в workflow.

Для дополнительной защиты следует запретить вход `root` по паролю, оставить
только авторизацию ключами, настроить firewall и fail2ban. Следующий шаг
усиления изоляции — отдельный пользователь `deploy` с минимально необходимыми
правами вместо `root`.

Само приложение доступно пользователям из интернета через порты 80 и 443.

## Как устроены сборка и выпуск

### 1. CI

При каждом pull request и push в `main` запускается
`.github/workflows/ci.yml` на GitHub-hosted Ubuntu 24.04, где доступен
зафиксированный в `.ruby-version` Ruby 4.0.2. Параллельно выполняются:

- `scan_ruby` — Brakeman и аудит зависимостей;
- `lint` — RuboCop;
- `test` — тесты Rails с PostgreSQL 16: сначала `bin/rails db:test:prepare test`,
  затем загрузка справочных данных и повторный `bin/rails test` вместе с
  `bin/rails test:system` (каталог `test/system`).

Если хотя бы одна проверка завершается ошибкой, автоматический выпуск не
запускается. Отдельного job `system-test` нет: системные тесты выполняются в
job `test` после загрузки справочных данных.

### 2. Docker-образ

После успешного CI для push в `main` запускается
`.github/workflows/deploy.yml`. Workflow проверяет, что прошедший CI коммит
по-прежнему находится на вершине `main`, и собирает его образ по корневому
`Dockerfile`. Workflow также можно запустить вручную через `workflow_dispatch`.

Dockerfile использует многоступенчатую сборку:

1. Базовый слой основан на `ruby:4.0.2-slim`.
2. Во временном build-слое устанавливаются компиляторы и build-зависимости.
3. Выполняются `bundle install`, компиляция Bootsnap и Rails assets.
4. Готовое приложение и gems переносятся в облегчённый runtime-слой.
5. Приложение запускается от непривилегированного пользователя `rails`.

Build-инструменты временного слоя в итоговый образ не попадают. BuildKit
сохраняет слои в кэше GitHub Actions для ускорения следующих сборок.

### 3. GHCR

Образ публикуется в GitHub Container Registry с уникальным тегом сборки и
удобным mutable-тегом:

```text
ghcr.io/sas2job/leave-desk:<SHA>-<run-id>-<run-attempt>
ghcr.io/sas2job/leave-desk:latest
```

Production использует не тег, а возвращённую BuildKit ссылку
`ghcr.io/sas2job/leave-desk@sha256:<digest>`. Поэтому повторная сборка того же
SHA получает отдельный тег запуска и не меняет образ прежнего релиза. Тег
`latest` предназначен только для удобства и не определяет работающий релиз.

### 4. VPS

GitHub Actions выполняет следующие действия:

1. Настраивает временный SSH-ключ и проверяет host key сервера.
2. Загружает `deploy/compose.yml`, `deploy/Caddyfile`, служебные скрипты и
   service/timer-файлы в отдельный `.incoming`-каталог, проверяет SHA-256
   manifest и атомарно переключает ссылку `current` на полный релиз.
3. Временно авторизует Docker на VPS в GHCR токеном текущего workflow.
4. Читает точный digest образа из `current/release.env`; секреты остаются в
   серверном `.env`.
5. Выполняет:

   ```sh
   ./current/compose.sh pull web migrate
   ./current/apply-migrations.sh
   ./current/compose.sh up -d --no-deps web
   ./current/apply-caddy.sh
   ```

Скрипт миграции проверяет поколение схемы релиза, останавливает прежний `web`,
согласует `db` через Compose, запускает `migrate` и после успеха монотонно
обновляет стабильный `schema-rollback-floor`. При ошибке `web` остаётся
остановленным. Compose пересоздаёт PostgreSQL при изменении его конфигурации;
том данных сохраняется. `apply-caddy.sh` проверяет кандидат из релиза командой
`caddy validate` до изменения действующего файла, затем размещает временный
`.Caddyfile.next.XXXXXX` в серверном каталоге `caddy`, атомарно заменяет
`caddy/Caddyfile`, согласует контейнер через Compose и выполняет явный reload.
Compose может пересоздать Caddy, особенно при переходе со старого bind mount;
обещания отсутствия перезапуска нет. Скрипт ограниченно ждёт готовности admin
endpoint. При ошибке после замены он пытается восстановить прежний файл,
пересоздать Caddy с ним и повторить reload. Если восстановление работающей
конфигурации не подтверждено, требуется ручная проверка. Ошибка кандидата
останавливает deploy до health checks, но уже выполненные миграции и обновление
`web` автоматически не откатываются. После выпуска авторизация GHCR удаляется
с VPS.
После запуска сервисов workflow проверяет действующий Docker `LogConfig` для
`caddy`, `db` и `web`. После успешного внутреннего health check он устанавливает
таймеры резервного копирования и очистки файлового кеша, проверяет загруженные
unit-файлы и запускает службу очистки один раз; при ошибке выпуск завершается
неуспешно.

Откат через `current/rollback.sh` использует локальный образ по сохранённому
digest без входа в GHCR. Если образ уже удалён из cache, оператор передаёт
read-only токен через stdin; скрипт использует и удаляет отдельный временный
Docker config. Старые каталоги релизов с SHA-тегами временно поддерживаются,
но новые релизы с mutable-ссылкой публикация отклоняет.

До обращения к Docker rollback отклоняет релиз, чьё значение
`schema-compatibility` ниже сохранённого floor; релиз без метаданных считается
предшествующим первой границе совместимости.

### 5. Проверка выпуска

После успешного `apply-caddy.sh` workflow ждёт запуска Rails и проверяет `/up`
через локальный порт приложения.
В запрос передаётся разрешённый host из серверного `.env`. Каждая попытка
ограничена двумя секундами на соединение и пятью секундами на весь HTTP-запрос,
а вся серия — жёстким сроком 90 секунд. Если endpoint не отвечает успешно за
30 попыток или общий срок истекает, deploy сообщает причину, завершается
ошибкой и выводит последние 100 строк логов контейнера `web`. Затем отдельным
шагом проверяется публичный `https://$DEPLOY_HOST/up`; его ошибка также делает
workflow неуспешным. При сбое выпуска проверяйте состояние `web`, Caddy и
`schema-rollback-floor`; откат через `current/rollback.sh` разрешён только к
совместимому поколению схемы и не отменяет миграции.

## Где находятся секреты

В GitHub Environment `production` хранятся:

- `DEPLOY_HOST`;
- `DEPLOY_PORT`;
- `DEPLOY_USER`;
- `DEPLOY_SSH_PRIVATE_KEY`;
- `DEPLOY_SSH_KNOWN_HOSTS`.

Пароль PostgreSQL, `SECRET_KEY_BASE` и публичный адрес приложения остаются в
серверном `.env` и не передаются в репозиторий. Workflow читает на VPS только
`LEAVE_DESK_PUBLIC_HOST` для заголовка Host внутренней проверки; остальные
значения использует Compose без передачи в GitHub Actions.

Итоговый процесс: успешный push в `main` → CI → сборка образа → публикация в
GHCR → миграции → обновление контейнера `web` → применение Caddy → внутренний
и публичный health check.
