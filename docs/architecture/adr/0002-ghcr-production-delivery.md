# ADR 0002: доставка production-образов через GHCR

## Статус

Принято; идентификация образов уточнена в ADR 0023.

## Контекст

Сборка образа на рабочей машине требует ручной передачи архива на VPS, а
сборка непосредственно на VPS расходует ресурсы production-сервера и зависит
от его текущего состояния. Выпуск должен использовать тот же коммит, который
успешно прошёл CI, и поддерживать однозначный откат.

## Решение

После успешного CI основной ветки GitHub Actions собирает Docker-образ,
публикует его в приватном GitHub Container Registry с уникальным тегом запуска
и разворачивает полученный content digest на VPS по SSH. Адрес сервера,
SSH-ключ и запись `known_hosts` хранятся в GitHub Environment `production`, а
не в Git.
При сборке production-образа Bundler исключает группы `development` и `test`;
CI устанавливает эти группы отдельно для проверок. Итоговый runtime-слой
получает только зависимости, нужные приложению и служебным командам выпуска.
Токен GitHub Actions передаётся Docker только на время скачивания образа и
после выпуска удаляется из конфигурации Docker на VPS.
Откат сначала использует локально кэшированный образ по сохранённому digest без
обращения к registry. Если образ отсутствует, оператор передаёт отдельный
read-only токен GHCR через stdin; временный Docker config удаляется до
переключения релиза.

Перед доступом к environment отдельный job без production-секретов допускает
автоматический выпуск только после успешного CI, запущенного событием `push`
основной ветки исходного репозитория. Он сверяет SHA с текущей вершиной `main`:
устаревший CI не может развернуть прежний коммит после нового. Ручной
`workflow_dispatch` остаётся отдельным явным путём выпуска выбранного ref;
откат к сохранённому digest образа описан в процедуре развёртывания.

## Последствия

- VPS больше не выполняет сборку приложения и не хранит исходный код.
- Каждый выпуск связан с конкретным проверенным коммитом и неизменяемым digest;
  повторная сборка того же коммита получает другой тег запуска и не меняет
  идентичность прежнего выпуска.
- Выпуск зависит от доступности GitHub Actions, GHCR и SSH-доступа к VPS.
- Изменения основной ветки автоматически попадают в production после успешного
  CI, если коммит всё ещё находится на вершине `main`; доступ к environment и
  его секретам необходимо ограничивать.
- CI pull request, в том числе из fork с веткой `main`, не получает доступ к
  production job. Если более новый коммит уже появился на `main`, автоматический
  выпуск старого коммита пропускается.
