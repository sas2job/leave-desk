# ADR 0023: content-addressed production-образы

## Статус

Принято.

## Контекст

Тег, состоящий только из SHA исходного коммита, не доказывает неизменность
Docker-образа. Повторная сборка того же исходного кода может дать другой образ
из-за изменившегося базового образа или системных пакетов и затем передвинуть
тот же registry tag. Такой rollback возвращает не обязательно тот артефакт,
который прошёл первоначальный выпуск.

## Решение

Каждый запуск сборки публикует образ под уникальным тегом
`<commit-sha>-<workflow-run-id>-<run-attempt>` и дополнительно обновляет
неиспользуемый для выпуска тег `latest`. BuildKit возвращает manifest digest;
workflow проверяет его формат и передаёт в `publish-release.sh` ссылку
`ghcr.io/<repository>@sha256:<digest>`.

Новый release принимается только с digest-ссылкой и сохраняет её в
`release.env`. Compose, миграции и rollback используют именно эту сохранённую
ссылку. Повторная сборка того же commit SHA создаёт отдельный build tag и не
может изменить content-addressed identity уже опубликованного релиза.

Старые каталоги релизов с SHA-тегами остаются читаемыми `rollback.sh` на время
перехода; это исключение не разрешено для новых публикаций. Нижняя граница
отката и совместимость схемы определяются отдельно.

## Последствия

- выпущенный артефакт однозначно определяется registry digest, а не mutable
  tag;
- deliberate rebuild того же коммита имеет отдельную identity и историю;
- `latest` остаётся только указателем для оператора и не участвует в deploy или
  rollback;
- удаление manifest из GHCR по-прежнему может сделать некэшированный rollback
  недоступным, поэтому политика хранения registry остаётся эксплуатационным
  требованием.
