# ADR 0006: отдельные роли PostgreSQL для приложения и миграций

## Статус

Принято; права на действующем сервере проверены 14 октября 2026 года.

## Контекст

Официальный образ PostgreSQL создаёт `POSTGRES_USER` как суперпользователя.
Прежний сервис `web` получал пароль этой роли, поскольку запускал `db:prepare`
при каждом старте. Компрометация приложения в таком случае давала права
суперпользователя БД.

## Решение

Сервис `migrate` запускается до обновления `web`, выполняет `db:prepare` от
bootstrap-роли `leave_desk` и выдаёт роли `leave_desk_app` права подключения,
доступа к схеме, чтения и изменения таблиц, использования последовательностей.
Роль приложения не получает право создавать базы, роли и таблицы. Сервис `web`
получает только её пароль и больше не запускает миграции автоматически.

Первого администратора после миграций создаёт оператор интерактивной командой
в контейнере `web`. Для записи пользователя достаточно прав роли приложения.
Команда не принимает пароль в аргументах, не меняет существующего администратора
при повторном запуске и сериализует конкурирующие попытки создания.

## Последствия

- Выпуск требует отдельного runtime-пароля и успешного запуска `migrate` перед
  перезапуском `web`.
- Bootstrap-пароль остаётся доступен сервису БД и одноразовому сервису миграций;
  его нельзя передавать `web`.
- После миграций выдаются права на существующие объекты. Права по умолчанию
  покрывают будущие объекты, созданные bootstrap-ролью.
- На действующем сервере `web` подключается как `leave_desk_app`. У роли нет
  `SUPERUSER`, `CREATEDB`, `CREATEROLE`, права `CREATE` на четыре базы и схему
  `public`; есть `CONNECT`, `USAGE` и права чтения и изменения таблиц во всех
  четырёх базах. Проверка была только читающей и не меняла данные.
