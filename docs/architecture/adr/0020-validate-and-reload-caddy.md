# ADR 0020: проверка и применение конфигурации Caddy при выпуске

## Статус

Принято.

## Контекст

Копирование `Caddyfile` на VPS не обновляет уже запущенный процесс Caddy.
Проверка приложения на loopback также не подтверждает публичный HTTPS.
Некорректный файл нельзя оставлять вместо действующей конфигурации.

## Решение

Хранить действующий `Caddyfile` в стабильном каталоге `caddy`, который целиком
подключён в контейнер как bind mount. Кандидат входит в неизменяемый каталог
релиза и проверяется командой `caddy validate` в одноразовом сервисе Compose.
После успешной проверки кандидат копируется во временный файл на той же
файловой системе и публикуется атомарным переименованием. Каталожный bind mount
видит новый inode; существующий single-file mount при первом применении
пересоздаётся через Compose. Затем выполняется `caddy reload`.

Перед reload скрипт ждёт готовности admin endpoint Caddy с ограничением 20
секунд и отличает истечение срока от ошибки самого reload. После возврата
прежнего файла Compose принудительно пересоздаёт Caddy с этой конфигурацией,
затем повторяет проверку готовности и reload; неподтверждённое восстановление
выводится как предупреждение.

При обычной ошибке применения предыдущий файл восстанавливается таким же
атомарным переименованием, после чего Compose и reload возвращают его в
работающий сервис. Принудительное завершение может оставить старую конфигурацию
в памяти процесса или новую на диске, но не частично записанный файл; следующий
restart получает полный проверенный файл. После выпуска проверяется публичный
HTTPS с проверкой сертификата. Кандидат с ошибкой синтаксиса не меняет
действующую конфигурацию.
