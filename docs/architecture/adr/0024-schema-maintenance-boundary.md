# ADR 0024: maintenance boundary и нижняя граница отката схемы

## Статус

Принято.

## Контекст

Миграция `20261014144746_create_federal_calendars_and_snapshot_duration`
заполняет исторические длительности и делает
`leave_requests.duration_half_days` обязательным без default. Приложение до
`f3a6d30` вычисляло длительность при чтении и не записывало эту колонку.

Прежний workflow применял миграции, пока старый контейнер `web` продолжал
принимать запросы. Его новая запись после включения `NOT NULL` завершилась бы
ошибкой. Обычный возврат старого образа после миграции оставлял бы создание
заявок сломанным постоянно. Default длительности не подходит: он скрывает
несовместимость и сохраняет неверный снимок.

## Решение

Каждый operational-релиз содержит файл `schema-compatibility` с 14-значным
поколением последней несовместимой границы схемы, которую поддерживает его
writer. Для текущего приложения это `20261014144746`.

Стабильный файл deployment root `schema-rollback-floor` хранит уже применённую
нижнюю границу отката и может изменяться только вперёд. Скрипт
`apply-migrations.sh`:

1. проверяет поколение релиза и сохранённый floor;
2. останавливает сервис `web`;
3. запускает одноразовый сервис `migrate`;
4. только после успеха атомарно повышает floor.

Workflow заранее загружает образы, вызывает этот скрипт и запускает новый
`web` только после его успеха. При ошибке миграции writer остаётся остановленным,
а floor не повышается.

`rollback.sh` до проверки или загрузки образа и до переключения `current`
сравнивает метаданные целевого релиза с floor. Релиз с меньшим поколением,
включая старый релиз без метаданных после установки первой границы, отклоняется.
Rollback не выполняет обратные миграции и не уменьшает floor.

Исторические строки по-прежнему заполняются логикой исходной миграции по их
датам и календарным правилам. После миграции сохранённый снимок длительности не
пересчитывается процедурой выпуска или отката.

## Последствия

- На несовместимой границе есть короткое окно обслуживания между остановкой
  старого writer и готовностью нового.
- Безопасен штатный откат только к релизу с поколением не ниже сохранённого
  floor.
- Возврат через границу требует отдельной одобренной процедуры и совместимой
  резервной копии БД, а не обычного переключения образа.
- Для каждой будущей миграции нужно оценивать совместимость старого writer.
  При новой несовместимой границе метаданные релиза повышаются вместе с
  тестами порядка stop → migrate → start и запрета старого rollback.
